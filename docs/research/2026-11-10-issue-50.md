# Issue #50：正常访问学校网站时出现保留状态

来源：[Issue #50](https://github.com/cqu-moe/quick-login/issues/50)、[Jam](https://jam.dev/c/ff6036e3-c20e-4e85-8517-d348a152f6c9)。检查时间：2026-11-10，Asia/Shanghai。源码基线：`b6e00a9`，扩展版本：0.5.7。

## 结论与边界

已在用户当前 Chrome 的正式版 0.5.7 上复现完整链路：先确认弹窗“已就绪”、本地回执 `applied` 且 7 个 Cookie 全部匹配，然后正常经过 SSO 进入智慧教务；`JSESSIONID`、`CtLgrmkSWHBZO` 的值和部分属性变化，约 9 秒后回执变成 `foreign`，弹窗显示“正在保留已有学校登录”。主登录凭据 `SOURCEID_TGC` 全程与插件写入记录完全相同，页面成功进入 `/workspace/home`；中间没有输入密码、扫码或重装扩展。

根因是“整组 Cookie 仍与写入快照一致”和“学校登录会话仍可用”被合并成同一展示判断：任一辅助 Cookie 超出有限的续期例外，就失去整组验证并上报 `foreign`。合成测试还验证了只改变一个辅助 Cookie 的值就足以触发，不需要两者同时变化。

该行为是现有保护策略与测试明确保留的行为。它避免后台轮询把旧云端辅助 Cookie 重新覆盖到本地，却将“插件会话中的辅助 Cookie 已改变”与“外来登录”呈现成相同标题。0.5.7 改了这一分支的解释文字和显式切换进度，没有消除状态分类本身。

原始 Jam 没有提供变化前后的 Cookie 差异；当前浏览器的设备记录与 Jam 不同，因此不能把这次现场捕获追溯为录屏那一刻的具体 Cookie 差异。现在确认的是同一正式版本、同样提示和正常访问路径可以在真实浏览器中完整重现。Cookie 事件没有写入者身份，不能仅凭 `cause=explicit` 断言具体响应或代码；本次没有捕获并归因原始 Set-Cookie 响应。

## 当前浏览器完整复现（2026-11-10）

只输出 Cookie 名称、属性名和相等性布尔值；真实值与摘要均留在扩展调试上下文内比较，没有写入诊断文件。临时观察器只读 Cookie 和扩展状态，未改写它们。恢复基线使用扩展现有“切换到快捷登录”动作一次。

1. 点击该动作后，弹窗从“正在准备学校登录”变为“已就绪”。观察器确认 `localWriteState=ready`、`receipt.result=applied`，7 个受管 Cookie 的精确摘要全部匹配。
2. 在临时标签页打开 `https://sso.cqu.edu.cn/login?service=https%3A%2F%2Fmy.cqu.edu.cn%2Fauthserver%2Fauthentication%2Fcas`，自动进入 `https://my.cqu.edu.cn/workspace/home`，没有交互式登录。
3. 以观察器安装为 t=0，t=11.115–11.116 秒出现两组 Cookie 覆盖事件。先移除旧值（`cause=overwrite`），再写入新值（`cause=explicit`）：

   | Cookie | 值 | 其他变化属性 | 导航后精确匹配 |
   | --- | --- | --- | --- |
   | `JSESSIONID` | 改变 | `sameSite` | 否 |
   | `CtLgrmkSWHBZO` | 改变 | `sameSite`、`expirationDate` | 否 |
   | `SOURCEID_TGC` | 不变 | 无 | 是 |
   | `SESSION`、`sidTheme`、`CtLgrmkSWHBZP`、`rg_objectid` | 不变 | 无 | 是 |

4. t=20.391 秒，存储事件首次显示 `localWriteState=idle`、`receipt.result=foreign`；t=25.794 秒的最终检查确认上述状态和 Cookie 差异。`schoolAccess` 仍为 `unverified`，所以不能把浏览器成功进入工作台写成扩展已经收到 `accepted` 证据。
5. 打开弹窗，确认标题与 Jam 完全一致：“正在保留已有学校登录”，并显示同步后状态变化的专用说明。没有再次点击切换来掩盖复现结果。

这说明重装不是触发该状态降级的必要条件；重新写入后也会在一次正常访问中复发。反复点击“切换到快捷登录”只能暂时恢复快照匹配，不能消除触发条件。

诊断结束已移除事件监听、清除定时器和调试全局对象，关闭临时标签页与本次打开的 DevTools；保留用户原有标签页。未修改权限、卸载扩展、清空存储或手工设置 Cookie。

## 用户补充的完整操作顺序

用户随后澄清：先登录过学校账号，之后卸载并重装 QuickLogin；重装后在**插件弹窗和 Auth 网页两个地方**都看到“已就绪”；接下来只是正常访问学校网站，没有再次输入密码或扫码，状态才变成“正在保留已有学校登录”。此前的登录发生在重装前，不能记为状态降级期间重新手动登录。

这使排查重点落在重装后已经就绪的会话再次变化。当前版本的插件弹窗必须取得本地 applied 回执及匹配的服务端 ACK 才显示已就绪；本地回执明确为空时，不会借用 Auth 的旧回执显示已就绪。结合用户确认，不能仅用“卸载导致旧 Cookie 所有权丢失”解释完整顺序。

这份重装时间顺序来自用户补充。Jam 没有录到卸载、重装或首次建立本地回执的过程；本次真实浏览器复现覆盖“已就绪→正常访问→保留状态”，没有重新执行卸载重装。

## 录屏证据

- 约 2.472 秒，Auth overview 返回云端 `ready`、已应用回执，设备上报版本 0.5.7，构建 `3ebd9d7479c3af201295c9eef838650ef4099471`。
- 23.5 秒与 34 秒，弹窗均显示“正在保留已有学校登录”，说明为“学校登录状态在同步后发生了变化；如仍能正常访问学校网站，无需重复切换。”这段说明专属于本地回执 `result=foreign` 的分支。
- 约 35 秒，智慧服务进入 `/workspace/home`，后续画面仍为已登录工作台。因此录屏没有证明学校登录失败。
- 48 秒及 55 秒的 DevTools 画面显示扩展后台 reconcile 请求上报 `cookieState: foreign`，版本仍为 0.5.7；状态不只存在于弹窗缓存。
- Jam 的结构化网络记录没有该扩展 worker 的 reconcile 请求，也没有 SSO 主机请求；上面两条 worker 证据来自画面。控制台工具返回零条记录，不能据此宣称后台没有错误。

## 反馈循环与对照

临时诊断测试复用 `src/background/sync-v3.test.ts` 的 Chrome fake、真实 `applyEnvelope`、`sync`、`handleMessage(GET_UI_STATE)` 和 `derivePopupView`。只在 API 边界使用已有 fixture，服务器始终返回可用会话；不改生产逻辑，不使用真实 Cookie。

最小步骤：写入 TGC 和 SESSION → 同步并确认“已就绪” → 只改变 SESSION 值 → 再次同步 → 断言仍为“已就绪”。去掉 SESSION 变化，断言通过。

实际执行的临时诊断命令：

```sh
npm test -- src/background/sync-v3.test.ts -t 'issue50 diagnostic'
```

首次两组对照：1 passed、1 failed，785ms；扩展为四组对照后两次结果一致，最后一次 778ms。唯一失败均为辅助 Cookie 变化后的标题断言：

```text
Expected: "已就绪"
Received: "正在保留已有学校登录"
```

这里的 RED 验证“没有更换主登录也会离开已就绪”这一症状，不是对改变后的整组 Cookie 仍然可信的证明。

| 输入变化 | 对照结果 |
| --- | --- |
| 没有变化 | TGC 为 managed，回执 applied，标题“已就绪” |
| 只改变 SESSION 值 | TGC 为 managed，回执 foreign，标题及说明与 Jam 一致 |
| 改变 SESSION 后恢复原值并再次同步 | 回执恢复 applied，标题回到“已就绪” |
| 改变 TGC 值 | TGC 为 foreign，localWriteState 为 foreign_session，回执清空，使用另一段说明 |

上述对照隔离出辅助 Cookie 变化分支；无需弹窗缓存故障或云端不可用即可复现。真实 Cookie 名称来自上面的现场观察，合成测试中的 `SESSION` 仅为最小变量。

### 重装状态的差分验证

[Chrome 官方文档](https://developer.chrome.com/docs/extensions/reference/api/storage)说明卸载扩展会清除 `storage.local`。针对用户补充，临时诊断在实际同步完成后清空合成扩展的 local/session 存储，重新通过真实 `readLocalState` 创建身份和空的所有权记录；重新授权阶段仅用状态 fixture 建模，不模拟 OAuth UI 或实际 Chrome 卸载。

执行 `npm test -- src/background/sync-v3.test.ts -t 'issue50 reinstall diagnostic'`，耗时 839ms：

- 保留合成旧 TGC：即使 Auth fixture 显示 ready，本地弹窗也不会先显示已就绪；同步直接进入 `foreign_session`，本地回执为空，不覆盖 Cookie。这个场景的所有对照断言通过，但不能复现用户描述的“先就绪、后变化”。
- 另一个对照先移除合成旧 TGC，使新安装可以重新写入并取得 ACK：确实先显示已就绪；随后只改变 SESSION 值，回执变成 foreign，预期继续已就绪的断言变红。这个场景验证重建后的会话仍有同一状态降级路径；**移除 TGC 是实验对照，不是用户操作或现场事实**。

不能据此断言用户清过 Cookie、旧 TGC 已消失，或者重新安装本身造成后续变化。当前确认的是：旧所有权丢失会直接保护旧登录；已经确认写入后的辅助 Cookie 变化则可以产生录屏里的另一条 foreign 分支。临时测试已删除，生产源码保持原样。

## 代码路径

- `src/background/cookie-store.ts` 的 `inspectCookieContinuity` 检查整组已管理 Cookie。仅辅助持久 Cookie 的到期时间延长有受限例外；值改变、其他属性改变仍返回 `changed`。
- `src/background/sync.ts` 的 `runSyncInner` 在整组 `changed`、TGC 仍为 `managed` 时，把旧回执改为 `foreign` 并清除应用验证状态。相同云端会话的例行轮询停止重复写入；显式切换、学校恢复和新会话保留各自入口。
- `src/background/api-v3.ts` 的 `localCookieState` 将 `receipt.result=foreign` 上报为 `cookieState=foreign`；共享展示逻辑优先将其映射到保留状态。因此这不只是弹窗的旧文字或缓存，也会影响 Auth 接收的设备状态。
- `src/popup/view-model.ts` 的 `derivePopupView` 为这个回执提供录屏中看到的专用解释，标题仍来自共享的 foreign 展示状态。

## 0.5.8 修复与回归（2026-11-10）

用户随后明确要求修复正常 Cookie 变化的误判，并保留真正外来登录保护。修复留在现有 Cookie 连续性检查，没有新增协议状态、依赖或存储。首次应用仍逐项精确读回；后续检查要求完整当前 TGC 集合精确属于原受管记录，且全部受管 Cookie 仍存在于原 store/domain/path。辅助 Cookie 的值和属性变化不再作为换账号证据。学校登录表单依然触发恢复，不将“已就绪”等同于所有学校业务登录成功。

原始所有权摘要始终保留，清理、替换清理、回滚及切换的一次性授权边界未放宽。删除了只服务于旧续期例外的 renewal 记录生成；旧版本已存的额外字段不参与判断，无需迁移。旧 foreign 回执在同一 TGC 被重新确认后沿现有逻辑恢复 applied 并补 ACK，Auth 继续使用原协议接收状态。

扩展原有同步测试：真实 applyEnvelope 写入后，合成持久辅助 Cookie 和 JSESSIONID 改值、改 SameSite，辅助有效期延长；覆盖已 ACK、等待 ACK、旧版本误判 foreign 三种起点。生产修复前，3 个 rotation 用例均在标题断言变红，3 个纯续期对照通过（793ms）；修复后 6/6 通过（598ms）。断言包括 popup 已就绪、上报 applied、不重复导出或写 Cookie，以及关闭后保留变更后的辅助 Cookie。外来 TGC 的值、属性、域、路径和缺少所有权证据仍拒绝；等待文档复用同一连续性检查，主登录变化和取消边界仍阻止导航。
